## 接続停止の調査と修正

従来の長い説明・URLを含むUser-Agentでは、DNS・TCP接続・TLS検証が完了しても本文が返らず、robotsと使用条件の取得がタイムアウトした。同じ識別名を短い標準形式 `DisneyCrowdAI/3.1` にした実際の通信は正常に応答した。原因はUser-Agentの形式に依存する応答停止まで確認できた。提供元の内部ルールや文字数制限は確認できていない。

ただし、この改善は手元の環境での結果である。同じ短い識別子を使ったGitHub標準4環境では読み取りタイムアウトとなった。Ubuntu・Intel macOSのcurlでも、HTTP/1.1とHTTP/2の双方でDNS・接続・TLS検証が完了した後、本文の先頭を受信せず停止した。HTTPの拒否応答は受信していない。提供元・配信経路の内部設定は不明であり、特定クラウドの禁止や地域制限とは断定しない。タイムアウト延長だけを解決策にはしない。

専用の `official_source.py` に通信を分離した。ブラウザー、検索エンジン、人の識別子への偽装、プロキシ、認証・購入ページへのアクセスは使わない。新しい依存ライブラリーや有料サービスは追加しない。

診断だけに使う `python diagnose_official.py --transport-check` は、通常クライアントのrobots読み取りタイムアウト時だけ、同じ識別子のcurlでrobotsの通信時間を比較する。401・403・429や条件変更時には別の通信で再試行しない。DBは変更しない。

## 公式情報へのアクセス条件

毎回、[robots.txt](https://www.tokyodisneyresort.jp/robots.txt) → [法的制約と使用条件](https://www.tokyodisneyresort.jp/legal.html) → 両パークの提供店舗一覧 → 各店舗メニュー、の順で取得する。robotsが取得できない場合やメニューが許可されない場合は停止する。現在の禁止対象 `/iframe/`・`/app/` は取得対象に含めない。未対応のAllow・ワイルドカード規則が追加された場合も再確認のため停止する。

使用条件の主要本文を正規化したSHA-256と確認範囲を `data/official-source-policy.json` に記録する。本文の変更・設定の欠落・想定外のHTMLを検出したら、商品を更新せず手動確認へ戻す。変更時に自動で新しいハッシュを承認しない。robotsの許可とコンテンツの再利用許諾は別に扱う。商品名・価格・日付・販売先・公式リンクという最小限の事実を保存し、画像・説明文・HTMLは公開データに保存しない。

要求開始の間隔は2秒以上、1調査100要求以内、接続5秒・読み取り15秒。タイムアウト・接続障害・一時的なサーバーエラーは1回だけ再試行し、3回連続失敗で通信を打ち切る。401・403・429では直ちに以後の通信を停止し、別の接続経路で回避しない。robotsの待機時間指定があれば長い方を守る。各要求の対象パス・時刻・HTTP状態・受信量・所要秒数と、確認した条件のハッシュを試行記録に保持する。

## 実行・再試行・保存

- 毎週月曜06:00 JSTに通常調査する。GitHubの起動遅延・欠落はあり得る。
- 毎日06:17 JSTに未完了の週を再確認する。同じ週の最新の自動試行が成功なら公式サイトへの要求は0回で終了する。成功後に強制再確認が失敗した場合は再び再確認対象となる。
- GitHub Actions → Update official alcohol menu facts → Run workflowで手動実行する。通常はforceをオフにし、完了済み週を実際に再取得したい場合だけオンにする。
- 接続の小規模な確認には手動専用のDiagnose official source connectivityを使う。DBを更新せず、robots・使用条件・ランド一覧・最初の店舗メニューを確認する。

完全成功時だけ全体の最終成功時刻を更新する。部分失敗・全体失敗の試行と理由は残す。前回の商品・価格履歴・期間・管理者補足を保持し、解析失敗を販売終了とみなさない。商品詳細が確認できない提供店舗は、その状態を表示する。

既存の `crowd-data`、共通の書き込み順序制御、SQLite整合性確認、差分記録・チェックポイント・バックアップを継続する。再確認を見送った場合は `collection_performed=false`、`source_requests_this_attempt=0`、`attempt_finished_at_utc` を残す。元の成功記録にある要求数・最終成功時刻と、今回の見送り時刻を混同しない。

## 手元の取得による復旧

`alcohol_local.py` は最新のcrowd-dataを入力として、新しい作業フォルダーへDBの整合性を確認したコピーを作り、同じ識別・条件確認・収集処理を実行する。元のDBは変更しない。公開するファイルの一覧・SHA-256・Git blob SHA、入力のデータブランチのコミットを `publication.json` に残す。9テーブルの既存キーが失われた場合は公開準備を中止する。SQLiteはバックアップ機能で単独ファイルにし、WALへの依存を残さない。

```text
python alcohol_local.py --source-directory <最新の保存データのフォルダー> --output-directory <存在しない新しい作業フォルダー> --base-sha <入力したcrowd-dataのコミットSHA>
```

このコマンドだけではGitHubに送信せず、常駐もスケジュール登録もしない。認証情報は保存しない。公開には所有者の既存GitHub接続を使い、manifestにあるalcohol.db・最終試行JSON・新しい圧縮差分・必要時のチェックポイントだけでtreeを作る。各blobの返却SHAをmanifestと照合し、入力時のブランチ先頭SHAを指定して参照を更新する。先頭が進んでいれば拒否される。古いDBをforce pushしてはいけない。最新DBに取得済みの差分をマージして再確認するか、準備ファイルを保持して報告する。ランド・シーのDBは送信対象に含めない。

実取得の試行には `execution_environment` を保存し、手元の取得をGitHubでの取得成功と表現しない。手元で成功した週にGitHubの再実行が通信0回で成功しても、それは復元・同週の見送り・保存の確認である。

所有者の選択により、既存のCodexアプリに「アルコール情報の週次補助更新」を毎週月曜06:30 JSTで登録し、ACTIVEを確認した。PCとアプリが動いている必要がある（[公式の定期実行の説明](https://learn.chatgpt.com/docs/automations?surface=app)）。通常のCodex利用が発生する。新しいWindows常駐ソフトや有料契約は追加していない。設定はアプリのScheduledで管理し、リポジトリを複製するだけではこの補助実行は登録されない。GitHubの再試行は維持する。最初の月曜の実起動・自律実行はまだ未確認である。

2026年10月31日01:48:47〜01:50:22 JSTには、この手順で全44店舗・48要求を実際に確認し、全要求200、164商品、価格164件、日付32件を保存した。商品詳細を確認できたのは43店舗で、1店舗は詳細未確認のまま保持する。crowd-dataへの反映は `e058c19fbd9e532bafd0b39fb4ba825b0c4d37a6`。元の成功・失敗履歴、価格・期間、345件の差分、全ての既存journalを保持した。両パークのDBは同一バイト列で、差分からの復元・二重投入0件・再起動相当の復元を確認した。これは手元の実運転結果である。
