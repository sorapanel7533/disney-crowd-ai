# Stage 3 運用手順

公開URLと既存7画面、元DB、Git履歴を維持し、8番目の「アルコール情報」を追加した。採用モデルは `legacy-corrected-v1`。長期の起動安定性・精度改善は未証明で、完成判定はBを維持する。

## 待ち時間収集

cronは08:07〜21:52 JST、15分間隔を維持する。GitHubのscheduleは遅延・欠落し得るため、通常の定期起動から最大330分の有期限セッションを開始し、実際の時刻で15分ごとに取得・採点・保存する。22時以降は停止。ジョブ上限350分。Windowsの常駐処理や追加サービスはない。開始が遅れた時間帯の過去値を現在値で補完しない。

各標本の直後にSQLite・差分・`collection-attempts.jsonl` をcrowd-dataへ保存する。途中で落ちても保存済みの標本は残る。実行ID・再実行番号・標本番号を差分名に含める。両ワークフローで共通のconcurrencyを使い、保存先への書き込みを直列化する。GitHubは待機ジョブの全件実行を保証しないため、起動数だけで観測率を判定しない。

同じ観測キーは再保存しない。5分以内の取得が保存されている場合、通常セッションは重複要求を見送る（所有者のforce実行は明示的な再確認）。API失敗・DB保存失敗・DBオープン失敗・予測/関連情報処理失敗を分類する。API自体の短い再試行と、次の実時刻での再取得を行う。Git pushは同じコミットを最大3回送信し、force pushは行わない。保存失敗時のDB・差分をActions artifactに7日保持する。

管理画面「定期収集の観測率・3日間判定」は08:00〜22:00の各15分枠について、既知の施設数（ランド37、シー36）の80%以上の有効な状態観測を必要とする。施設の増減時は分母を更新する。観測時刻で集計し、未起動枠を成功扱いしない。終了済み3日間の観測率80%以上は暫定目標であり、学習に使える営業中履歴の充足率とは別の指標。学習側は引き続き09:00〜21:00の仮定を明示する。

方式比較：cronのみは短い実行時間だが欠落に弱い。有期限セッションはrunnerを待機中も使用し、最大約840分/営業日という時間コストがあるが、起動後の観測を確保できる。欠落後の再起動は将来の取得を再開できても過去値を回復できない。外部スケジューラーは認証・登録・保守が増えるため採用していない。この公開リポジトリの標準Linux runnerを使い、有料サービスは追加しない。無料条件の変更や非公開化時には利用枠を再確認する。

[GitHubのschedule仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 21時台の予測と継続比較

10月30日21時台の起動・翌31日用固定予測は保存履歴に存在しなかった。後から時刻を戻して発行しない。所有者はActionsのCollect park observations → Run workflowを実際の21時台に実行できる。時間外の手動実行は通常の未来向け予測を現在の発行時刻で保存し、21時発行を装わない。

通常予測は対象15分終了後、有効な実測だけで採点。比較予測は対象1時間が終了し、異なる15分枠3個以上の実測がある場合に採点。7日経過後も不足なら不足状態を残す。通常予測のerrorは実測−予測、比較および報告のBiasは予測−実測である。

比較用に旧・現行・曜日時間中央値・重み候補・新しい直近傾向候補の5版を保存する。新候補のコードとパラメータはSHA-256で固定し、評価日で調整していない。検証済みで発行前に利用可能だった履歴だけを渡す。新候補は直近1時間に十分な営業中標本がある場合のみ、水準差と増減を小さく加える。将来の天気実績・価格・誤差は使わない。休止は学習から除き、再開後に標本が揃うまで直近補正を行わない。複雑な学習器は追加しない。

営業中は時間単位で新しい比較発行を行い、21時台は翌日9〜20時用を別発行する。元の比較予測は保持する。MAE/RMSE/Bias、パーク・主要/非主要・日・時間・リードタイム、候補別の日単位不確実性を保存。14日以上の独立した充足日、3期間、対応比較、10%改善目標、bootstrapを必要とし、自動採用しない。30日以上や季節を跨ぐ検証は別途必要。旧モデルの非主要施設予測が存在しない場合、その制約とモデルごとの標本数を明示する。

2026年5月8日の診断は1日だけで正式な独立評価ではない。新候補は時間集約された診断では重み候補へフォールバックして同値になり、追加改善を示していない。正式な評価準備済みの日数は現在0。新候補も未採用。ロールバックは通常のrevertとCIで行い、履歴を書き換えない。

## アルコール情報

2026年10月31日の接続・週次再確認・絞り込みの改修は [週次更新の運用記録](WEEKLY_ALCOHOL_OPERATIONS.md) を参照。以下の初回接続失敗は、改修前のStage3検証時点の記録である。

独立した `alcohol.db` の9テーブルに商品・店舗・販売関係・期間・価格履歴・試行・出典・差分・管理者補足を分離する。公式food IDを優先する。価格表に商品IDがない通常ドリンクは店舗IDと正規化名称の組を使うため、店舗間で同名でも同一商品と推定統合しない。掲載商品数はこのキーの数である。

公式一覧のアルコール提供タグ6006から両パークの店舗を取り、店舗別メニューのアルコール表示およびビール/ワイン等の明示された飲料区分を解析する。ノンアルコール、カクテル風の一般ドリンク、パーク外は除外。商品を取得できない提供店舗は「提供店舗・商品詳細未確認」。価格表の複数サイズは価格表示全体を保持し、単一価格へ推定しない。日付がない通常商品は期間未確認とし、販売期間内検索に混ぜない。販売開始前・期間終了・期間途中の休止を区別する。在庫・営業をリアルタイム確認したと表現しない。

週次更新は月曜06:00 JST（UTC日曜21:00）。ActionsのUpdate official alcohol menu factsで手動再確認できる。同じ週の自動調査が正常終了していれば再投入を見送り、forceで実際の再確認を可能にする。各失敗試行を保持し、部分更新で全体の最終成功時刻を新しくしない。8日で注意、14日で警告。閲覧では公式サイトへ収集アクセスせず、DBとcrowd-dataだけを読む。

アクセスは識別可能なUser-Agent、2秒以上の間隔、100要求以内、短いtimeout、3失敗で通信を打ち切る。robotsを毎回確認し、/iframe/・/app/、認証・購入系にはアクセスしない。拒否・失敗を回避する偽装や別認証は使わない。初回はこの作業環境の直接取得がtimeoutとなったため、通常のブラウザーで公式一覧と44店舗の見出しを照合して調査した。公開後のActions初回も公式接続に失敗し、前回の164商品と失敗記録を保存した。週次の自動取得成功は未確認であり、完成扱いしない。robotsを取得できなければ安全側で調査を停止する。接続可能になった際に所有者の手動実行または週次実行で再試行する。

[公式の使用条件](https://www.tokyodisneyresort.jp/legal.html)はコンテンツ転載を制限している。画像・写真・HTML・説明文をサイトやリポジトリへ転載せず、独自の説明と商品名・価格・日付・販売先という最小限の事実、公式リンクだけを保存する。画像の再利用許諾は確認していないため画像は表示しない。情報の事実性と、素材の使用許諾を混同しない。条件が変わった場合は自動処理を停止して手動確認へ戻す。

店舗の解析失敗は消失・販売終了にしない。既存商品が30%超減る店舗と店舗一覧が20%超減るパークは審査対象として保持する。小さい掲載削除も販売終了とは別の状態。通常の終了は公式掲載の販売終了日で判定する。過去の価格・期間・掲載関係・差分は削除しない。

## 管理者と永続化

管理者秘密値が未設定なら共有情報の編集は拒否。所有者がStreamlitのManage app → Settings → Secretsへ `ADMIN_PASSWORD_SHA256` を設定する。十分長い専用パスワードから所有者の端末で生成し、平文・トークンをGit・DB・ログ・チャットへ載せない。設定前の認証テストは隔離DBだけで行う。

アルコール管理者補足は公式データと別テーブル。画面から補足JSONをダウンロードし、GitHubの週次調査のRun workflow → admin_noteへ貼り付ける。所有者のGitHub権限での実行を永続保存の境界とする。Actionsが検証・保存して、DBにacknowledged_at_utcとevent_idが入り、次のサイト同期で補足が戻ることを確認する。準備済みJSONや送信成功だけで保存済みとしない。自動収集は補足を上書きしない。追加トークンはこの経路に不要。

SQLite全体の保存と不変の圧縮差分を維持。両パークとアルコールの破損検査を別々に行い、アルコール障害で収集を止めない。新しい空DBへスキーマを作り、`data_journal.replay` を時系列順に適用できる。同じ差分の再投入は重複しない。`persistence.snapshot` と `merge_snapshot` で整合性検査付き復元を行う。crowd-dataを含む全履歴は `git bundle create backup.bundle --all` で保全する。

保存容量は増加する。現在サイズ×56×30は「サイズ一定」の未圧縮試算で、将来上限でもGit圧縮後の実測増加でもない。DB合計20MiB、同期100MiBより前に月別分割/日次チェックポイントと差分再生への移行を検証する。現時点で長期容量問題が解決したとは扱わない。
